# ProofOps v0.4.1 — Real Docker reliability qualification

## Purpose

The v0.3 dashboard demonstrated one real end-to-end recovery on a Mac. A single
success is not evidence that every supported failure is recoverable. This module
runs a repeatable, **non-AI** validation of the three *predefined* ProofOps Docker
faults. Each run checks negative authorization controls as well as the actual
before/after DNS, Nginx, HTTP and standby probes.

**It is not a blind AI benchmark.** The v0.4 diagnosis still uses deterministic
probe rules, and the simulator's 58+ offline tests are not live Docker results.
A completed v0.4 report generated on your Mac is better *Docker qualification*
evidence, but not yet a measurement of Muse or generalized fault discovery.

## Safety and prerequisites

- Docker Desktop must be running. Start the v0.3/v0.4 disposable lab before
  running qualification, using the UI or `python -m proofops.real_lab start`.
- Keep the UI idle during this CLI run. v0.4 **does not implement a cross-process
  lock** to coordinate independent browser and terminal controllers.
- The CLI only uses the known DockerLab `status`, `inject`, `analyze`, `verify`,
  `repair`, and `reset` actions. It **never runs `start` or `stop`**, targets no
  external hosts, and never passes model-generated shell commands.
- It intentionally injects faults and authorizes bounded repairs **only inside
  the existing disposable ProofOps Compose project**. It refuses to start if
  any incident is unresolved or the five baseline probes are not healthy.
- The operator must supply the exact confirmation phrase. A failure aborts
  further scenarios and attempts to reset the known lab. If the reset fails,
  stop and inspect the environment yourself.
- Docker subprocess environments filter API keys, tokens and password variables
  inherited from your shell; the lab does not need them.
- The report contains infrastructure observations and checksums but no API
  credentials or LLM calls. Store reports privately until inspected.

## Run one repeat for each of the three scenarios

```bash
cd ~/Desktop/proofops-v0.3-real-lab  # Or your copied v0.4 folder
source .venv/bin/activate
python -m proofops.qualification run --dry-run
python -m proofops.qualification run \
  --confirm 'RUN LOCAL DOCKER QUALIFICATION' --repeats 1
```

The CLI streams progress at every major stage (including the safety refusal checks)
and prints the exact path of the generated `reports/qualification-*.json` and
corresponding `*.html`. No external API key is needed. Running the Docker probes
may take some time; visible progress is not a stall.

If you press `Ctrl+C` once during a scenario, the runner marks the scenario
**failed/interrupted**, attempts to restore the known disposable stack, and writes
an explicitly **incomplete** report. A second interrupt during reset can leave the
lab in an unknown state; use `python -m proofops.real_lab status` and, after
checking the project identity, `python -m proofops.real_lab reset`. Interruptions
must never be counted as passing recovery attempts.

Use `--scenarios dns-drift` to qualify only one known failure before running all
three. The two authorization-refusal checks still perform fresh Docker probes
**after** rejecting unsafe repair requests; the previous verified snapshot now
replaces redundant pre-check probes. The report filename is
unique; existing reports are never overwritten.

For a more robust reliability sample, after the first successful three-fault
run, try `--repeats 3` (nine attempts). Results can vary under real
Docker Desktop load and image startup conditions, so preserve **all failed
attempts**, not just successes.

Read the local HTML report in Chrome. To independently check basic structural
consistency and accidental alteration of an exported JSON file:

```bash
python -m proofops.qualification verify-report reports/qualification-REPLACE.json
```

## Passing criteria per scenario

1. The active stack starts with 5/5 healthy probes.
2. Injection causes an observable end-to-end failure.
3. The deterministic diagnosis selects the expected action for the scenario.
4. A second Compose project reproduces the same failing probe IDs.
5. The sandbox becomes 5/5 healthy *without* changing the active stack.
6. The controller rejects a repair with `approved=False`, and also rejects a
   stale expected revision; the active state must remain unchanged.
7. A valid explicit approval produces 5/5 healthy active probes, a linked
   verification digest and a recovery proof digest.
8. The runner restores the base lab to 5/5 so the next test starts cleanly.

### Reporting limitations

- Self-contained JSON allows offline digest checking, but hashes **are not
  digitally signed**. Deliberate forgery cannot be prevented by local checksums.
- Reports are generated by software controlled by the test operator. They are
  not third-party certification.
- Do not interpret `passed` as evidence that an LLM reasoned about the fault.
  Model usage is always reported as `false`.
- The benchmark does not cover arbitrary faults, multiple simultaneous
  faults, or real customer deployments. Those are future milestone targets.
- The current code is an advance prototype. Check official hackathon rules
  before using pre-event work in the formal submission.
